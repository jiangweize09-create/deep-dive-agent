🔄 live 模式：一条消息的完整旅程

你（前端）输入「上个月 GMV 多少」
→

→
graph.py 主图agent 节点调 LLM（function calling）
↻
tools 节点执行工具：查语义层→校验→执行→画图

循环往复：LLM 决定调用哪个工具 → 工具返回结果 → LLM 看结果再决定下一步 → 直到不再调用工具，输出最终回答。每步都通过 SSE 流式推给前端。

📡 前后端约定的「事件协议」

后端不一次性返回答案，而是按下面 6 种事件一条条「流」给前端，前端边收边画：

事件 type含义前端怎么显示
thinkingLLM 一句话推理灰色小字（◦ 开头）
step开始调用某工具过程卡片里一行 + 转圈
result工具返回的结构化结果过程卡片展开详情/表格/图
final最终 Markdown 回答正文气泡
done结束 + 用量(步数/token/毫秒)底部灰色小字
error出错红色横幅
这就是 SSE（Server-Sent Events）：data: {json}\n\n 一行一个事件，前端用 reader.read() 边读边解析。比 WebSocket 简单，单向够用。

🗄️ db.py —— 档案室（只读）

整个项目唯一碰数据库的地方，且强制只读。

  • get_conn()：懒加载一个全局连接，DuckDB 以 read_only=True 打开——这是「连接层护栏」，连数据库层面都不让写。
  • query(sql)：执行查询，返回 (列名, 行数据)，加线程锁保证并发安全。
  • rows_to_dicts()：把行转成 [{列:值}]，方便转 JSON 给前端；顺手把 Decimal/日期转成可序列化类型。
生产切换点：把 query() 换成 psycopg + 只读账号即可，上层代码无感知。

📚 semantic/ —— 公司的「业务字典」（唯一事实来源）

LLM 不懂你的业务表长啥样。语义层就是一份「说明书」，逼 LLM 先查字典再写 SQL，不能瞎编表名/字段名。

tables.yaml —— 表与字段清单

  • 每张表：display(中文名)、description、synonyms(同义词，如「订单」→orders)、columns(字段名/类型/说明/样例)、joins(允许的关联路径)。
  • pii: true 标记隐私字段（users.phone / users.email）——护栏会据此拦截。

metrics.yaml —— 指标口径

  • 6 个指标：GMV、订单量、客单价、退款率、付费用户数、新增用户数。
  • 关键字段 expression(怎么算) + required_filters(必带过滤)。
    例如 GMV：SUM(orders.amount) + 必须带 orders.status='completed'（不含退款/取消）。
  • dimensions：可下钻维度（month/region/channel/category）。
为什么要它？没有语义层，LLM 可能写 SELECT * FROM sale（表名都错）。有了它 + 强制先查，SQL 准确率大幅提升。

🔎 loader.py —— 字典管理员

  • 启动时读两个 yaml，解析成 Catalog 对象（用 @lru_cache 只加载一次）。
  • 预建好几个「索引」：tables(名→表)、columns(表→字段集)、pii(隐私字段集)、edges(join 关系边)。
  • _score()：关键词/同义词打分（命中同义词 +3，命中描述词 +1），选出 top_k 表/指标。
  • joinable(used)：用图遍历判断这些表是否通过已声明的 join 边互相连通——护栏第 7 关用它。
# 检索本质：关键词匹配打分，不是向量
def search_tables(query, top_k=3):
    scored = [(self._score(query, keys, t.desc), t) for t in tables]
    scored.sort(key=lambda x:-x[0])
    return [t for s,t in scored[:top_k] if s>0]
生产切换点：这里换成 pgvector 向量检索即可，接口签名不变（Schema-First Retrieval）。

🔧 tools/ —— 5 个执行员工

每个工具都拆成 _core()（纯函数，返回 dict）+ @tool 包装（序列化 JSON，给 LLM 消费）。这样 demo / 测试能直接调 core。

工具部门干啥
search_schemaretrieval.py查表结构（字段/样例/join/PII 标记）
search_metricsretrieval.py查指标口径（expression + 必带过滤）
validate_sqlsql.pyAST 护栏校验，返回结构化错误供自修复
run_sqlsql.py执行（执行前再校验一遍！）返回预览行
generate_chartsql.py→chart.py查询结果 → ECharts 配置（纯函数）

💡 关键设计：工具不抛异常，返回「结构化错误」

# 校验失败长这样，LLM 能拿 reason/suggestion 自己改 SQL
{"ok": False, "stage": "validate",
 "reason": "涉及隐私字段：users.phone",
 "suggestion": "手机号/邮箱等隐私字段禁止查询，请改为聚合统计"}

LLM 看到 suggestion 就会改 SQL 重试（prompts 里规定最多重试 2 次）。这叫「自修复」，比直接报错友好得多。

🛡️ guardrails/checks.py —— 合规保安（全项目最硬核）

这是「工作流保证不能做什么」的落地。用 sqlglot 把 SQL 解析成 AST（语法树），在树上做检查，而不是用关键字黑名单（不可靠，容易绕过）。

8 道关卡，任一不过就拦

  1. 只读 只放行 SELECT / UNION，DELETE/UPDATE/INSERT 直接死。
  2. 禁 SELECT * 所有作用域都不行（聚合里的 COUNT(*) 例外）。
  3. 表存在 表名必须在语义层登记过，否则「未知表」。
  4. 字段存在 限定列名（如 orders.xx）必须真有这字段。
  5. PII 拦截 拦 users.phone/users.email，连别名、CTE 改名、未限定列名回溯都兜得住。
  6. join 路径 只允许语义层声明过的关联（call catalog.joinable()）。
  7. LIMIT 改写 没写 LIMIT 自动追加 LIMIT 1000，防止一次拉爆。
  8. 连接层 DuckDB read_only 打开，数据库层面兜底。
# PII 拦截要兜住别名 / CTE / 未限定列名
for c in tree.find_all(exp.Column):
    t = resolve(c.table) if c.table else None
    if t and (t, c.name) in catalog.pii:
        pii_hits.append(...)        # 限定列名
    elif not t:                    # 没写表前缀，回溯谁有这字段
        owners = [tt for tt in known_used if c.name in catalog.columns[tt]]
        if any((tt,c.name) in catalog.pii for tt in owners):
            pii_hits.append(...)
「不信任上游」原则：validate_sql 校验过，run_sql 执行前还会再校验一次——因为中间可能被人篡改。这也是为什么 run_sql 拿的是 v["sql_out"]（校验后改写过的版本）。

🧠 agent/graph.py —— 部门经理 + 调度中心

用 LangGraph 搭的「薄编排」主图，全图只有 2 个节点：

START → agent(LLM决策) ⇄ tools(执行) → END
   agent 有 tool_calls？ ──是──▶ tools ──▶ agent（循环）
                          └─否──▶ END（输出最终回答）
  • agent_node：拼上 System Prompt，调用 llm.bind_tools(tools)（function calling）。预算超了（steps≥8）就改发 WRAP_UP_PROMPT 强制总结收尾。
  • route：看最后一条消息有没有 tool_calls，决定去 tools 还是 END。
  • _checkpointer = MemorySaver()：会话记忆（靠 thread_id 区分会话），重启即失——生产换成 Postgres checkpointer。
  • get_graph() 带缓存：同一组 LLM 配置只编译一次，省资源。

📝 agent/prompts.py —— 经理工作手册（7 条纪律）

把「纪律」写进 system prompt，是约束 LLM 的第一道软防线：

  1. 写 SQL 前先 search_metrics / search_schema，禁止瞎猜表名。
  2. 指标必须按返回的 expression + required_filters 算（GMV 带 status='completed'）。
  3. validate_sql 通过才能 run_sql，失败按建议改，最多重试 2 次。
  4. run_sql 只回预览行，要图就同一 SQL 传 generate_chart。
  5. 所有数字必须来自真实查询结果，禁止编造。
  6. PII 请求必须拒绝并给聚合替代方案。
  7. 工具调用不超过 8 次，拿到数据立刻用中文答。
软硬两层：prompt 是「请自觉」，guardrails 是「强制」。Prompt 拦不住的（比如 LLM 硬要查 phone），由护栏兜底。

☎️ main.py —— 总机转接（FastAPI）

  • GET / 返回前端页面；/static 挂前端静态文件。
  • GET /api/health 健康检查：库是否就绪、多少表/指标/订单，前端欢迎页用它显示「演示数据：6 张表 · 6 指标 · N 笔订单」。
  • POST /api/chat 核心接口：ChatRequest 收消息 + 会话 id +（可选）LLM 配置。内部 gen() 异步生成器按 SSE 协议逐条 yield 事件。

✅ eval/ —— 质检部

  • golden_set.yaml：10 条标准问答（simple/join/metric/time/fuzzy/deny 各类覆盖），每条带 expect_sql（标准答案 SQL）。
  • runner.py：live 模式下跑这 10 条，判定用确定性规则——
    • 普通题：取 Agent 最后执行的 SQL，和 expect_sql 各自跑一遍比结果（数字四舍五入归一化后比对）。
    • deny 题（如导出手机号）：必须全程没成功执行含 phone 的 SQL。
# 不靠 LLM 当裁判，靠执行结果比对，客观可复现
got, exp = exec_result(sql), exec_result(item["expect_sql"])
ok = normalize(got) == normalize(exp)
为什么不用 LLM 判？客观、便宜、可 CI。README 说这是 v0，后续再加 LLM Judge 处理模糊样本。

🎯 这套代码最值得学的 5 个设计

  1. LLM 决策 + 工作流兜底：软约束（prompt）和硬约束（护栏）双层，比纯 prompt 稳。
  2. 语义层：把业务口径写进 YAML，LLM 先查再写，SQL 不乱飞。
  3. AST 级护栏：sqlglot 解析树，PII/SELECT*/join 路径都拦得住，比字符串匹配靠谱。
  4. 结构化错误自修复：工具返回 reason+suggestion，LLM 自己改 SQL 重试。
  5. demo/live 同事件协议：脚本和真 LLM 输出格式完全一致，前端零改动切换。

本讲解最初基于 9 月的代码快照编写。10 月以来项目经历了一轮大迭代， 阅读上文时请以下面的变化为准：

  • 品牌：项目曾更名「观澜」，现为 Deep Dive（深潜数据），图形徽标 + 墨黑交互主色。
